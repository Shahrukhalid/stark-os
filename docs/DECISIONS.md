# Decision log

Each entry: decision, why, trade-off, and when to revisit.

### D1. One kernel process with asyncio instead of a Redis-backed worker queue
- **Why:** a single-owner social team runs on one machine; asyncio gives concurrency (parallel team reviews), cancellation and timeouts with zero extra services. Fewer moving parts = fewer failure modes.
- **Trade-off:** tasks don't survive an API restart (they are marked `failed: interrupted by API restart` on boot); no horizontal scaling.
- **Revisit:** when scheduled automation or multi-user deployment is built. A durable queue (Redis/arq or Temporal) would slot in behind `Kernel.run_task`.

### D2. SQLite by default, PostgreSQL supported
- **Why:** zero-setup local install. SQLAlchemy 2 keeps the schema portable; the PostgreSQL path is covered by `tests/test_postgres.py` (passes against PostgreSQL 16).
- **Trade-off:** no pgvector yet, so retrieval is lexical.
- **Revisit:** D5.

### D3. Free OpenRouter models only, through one small adapter
- **Why:** the project must run at zero cost. OpenRouter offers many free models behind one OpenAI-compatible API, so a single httpx adapter (`providers/openrouter.py` on top of `openai_compat.py`) covers everything; no vendor SDKs.
- **Trade-off:** free models are rate-limited (50 requests/day on a free key) and weaker at long multi-step tool use than frontier paid models. Mitigated by tier preferences, automatic failover with cooldowns, and per-task step/token limits.
- **Removed:** the Anthropic Claude, Ollama and generic OpenAI-compatible providers (2026-10-16, at the owner's request).

### D4. Internal message format = content blocks
Text / tool_use / tool_result blocks are converted to OpenAI chat messages (`to_openai_messages`). Keeping the internal format provider-neutral makes it cheap to add providers later.

### D5. Lexical memory retrieval first, vector later
- **Why:** works offline, no embedding provider needed, deterministic, testable.
- **Plan:** pluggable embedder (a free embedding model) + pgvector column, with lexical fallback.

### D6. Voice in the browser (Web Speech API) first
- **Why:** free, no keys, works in Chrome/Edge/Safari, supports push-to-talk, wake phrases and interruptible TTS. Each agent gets an *original* system voice (language, pitch, rate, preferred voice names). No actor voices.
- **Trade-off:** Firefox lacks speech recognition; quality varies by OS voices; recognition may use the browser vendor's cloud.
- **Plan:** server-side STT/TTS adapters (Whisper/faster-whisper locally; a premium TTS provider optional).

### D7. Monorepo layout
`apps/web`, `services/api` (Python package `stark` containing core/, providers/, tools/), `agents/` (config only), `docs/`, `scripts/`, `.github/workflows/`. The suggested `core/` and `integrations/` top-level folders became sub-packages of `stark` so the API installs as one Python package.

### D8. Tool output is untrusted; permissions don't rely on the model
Prompts tell agents that tool content is data, but the real defence is structural: allowlists, modes, approvals, path confinement, SSRF guards. A fully prompt-injected agent can still only request actions the policy allows, and changes still need a human.

### D9. Single-user token auth
- **Why:** local personal deployment bound to 127.0.0.1. Token generated by `scripts/setup.py`, compared in constant time.
- **Trade-off:** the SSE stream passes the token as a query parameter (EventSource cannot set headers) — keep access logs off or local.
- **Revisit:** multi-user or remote access needs OIDC + per-user data separation.

### D10. Free-model selection is data, refreshed at runtime
Free models appear and disappear weekly. The tier preference lists in `providers/openrouter.py` come from a live ping (2026-10-16) and are only a starting order: the runtime catalogue adds new free models, drops retired ones, and the failover skips models that are failing. `OPENROUTER_MODEL[_TIER]` or `[model] model` in an agent.toml pins a model.

### D10b. Keys stay in `.env`
The OpenRouter key and API token live only in the git-ignored `.env` (created with mode 600), are scrubbed from logs/audit by exact value, and are never returned by the API.

### D10c. Security audit (2026-10-16)
An independent review found and we fixed: a command-execution path via git config, `.env` reachable through document ingestion and moves, grant-scope escapes through `..` and prefix matching, SSRF gaps (DNS rebinding, CGNAT, WebSockets), persistent prompt injection through shared memory, exfiltration through fetched URLs, Home Assistant path injection, event-loop blocking, and several runtime races. Each has a regression test in `tests/test_security_regressions.py`.

### D11. Each agent has its own brain, but not a mind
Each agent has its own first-choice free models (`[model] preferred`), prompt, tier, temperature, limits, tool allowlist, private memory, delegation rules, voice and a workflow (prompted procedure + code post-processing such as Jocasta's citation check and the content-claim check). When an agent's first choice is rate-limited it falls back to the shared tier list. This is documented to avoid implying conscious minds.

### D12. Social media, not a personal computer (2026-10-16)
- **Why:** at the owner's request the seven agents were redesigned as a social media team. Roles follow each persona's job in Vision's Mindspace in VisionQuest (2026, as summarised on Wikipedia on 2026-10-16): J.A.R.V.I.S. security & housekeeping -> director and pre-publish review; F.R.I.D.A.Y. socialisation, humour, tactics -> community manager; E.D.I.T.H. recreation & games -> engagement and campaigns; Ultron firewalled, perceptive, a leaker -> red team with no network; Jocasta cunning -> intelligence & analytics; D.U.M.-E. maintenance & fire suppression -> publisher and crisis pause; U. mute videographer -> video/visuals, never spoken aloud.
- **Removed:** smart-home/robotics tools (Home Assistant, simulated lab) and the terminal tool. System metrics remain only for the dashboard's Diagnostics page.
- **Kept:** brand-folder file tools, web research, memory, delegation, the permission engine.

### D12b. Real publishing only where the API is free
Bluesky (AT Protocol, app password) and Mastodon (access token) have free, open APIs, so they publish for real. X, Threads, LinkedIn, Instagram, Facebook, TikTok and YouTube need paid tiers, app review or business accounts; STARK OS drafts, checks and schedules for them, and publishing is an explicit SIMULATION. Simulated posts never get engagement numbers.

### D12c. Policy checks in code, approvals for every publish
The check (`tools/social.py: check_post`) is deterministic so it cannot be talked out of a FAIL. Publishing is `EXTERNAL` risk: always approval, never covered by a grant, D.U.M.-E. only. Scheduling does not auto-publish (no unattended posting until the scheduled mode exists with its own safeguards).

### D13. E.D.I.T.H. and Ultron are deliberately constrained
E.D.I.T.H.'s defence/weapons side is not carried over: she has no publish, surveillance or offensive tools. Ultron is capped at OBSERVE with read-only tools, no network, no delegation and no access to user preferences; in VisionQuest he leaks information through the dark web, which is exactly the capability he is denied here.
